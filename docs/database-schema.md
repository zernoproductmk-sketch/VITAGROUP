# VITAGROUP — модель данных PostgreSQL v1

## 1. Цель

Одна центральная база должна одновременно поддерживать два контура:

1. **Производственный** — онлайн OEE, выпуск, ГП, брак, простои, ОТК, склад и сверка с ERP.
2. **Расчетный** — подтвержденная выработка сотрудников и расчет сдельной заработной платы.

При этом Coverse, Google Sheets, Excel и 1С:ERP являются источниками данных, но не «истиной сами по себе». Система хранит происхождение каждой записи и умеет сопоставлять факты между источниками.

---

## 2. Ключевые принципы

### 2.1. Смена

Для первой версии:

- ДЕНЬ: 09:00–21:00;
- НОЧЬ: 21:00–09:00 следующего календарного дня.

Каждая смена имеет собственный ID и фактические дату/время начала и окончания.

### 2.2. Источник данных

Для каждой внешней записи сохраняются:

- `source_system` — COVERSE / ERP / GOOGLE_SHEETS / EXCEL / WEB / SYSTEM;
- `source_record_id` — ID записи во внешней системе, если есть;
- `import_batch_id` — партия импорта;
- `created_at` — когда запись попала в нашу систему.

### 2.3. История

Нельзя незаметно заменить 300 шт. брака на 220 шт.

Изменение должно оставлять след:

- кто изменил;
- когда;
- что было;
- что стало;
- причина.

### 2.4. Подтверждение

Для зарплаты и управленческой отчетности используются не любые введенные данные, а данные, прошедшие необходимый статус проверки.

# 3. Справочники

## 3.1. users — пользователи сайта

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | ключ |
| email | text | логин |
| password_hash | text | хэш пароля |
| employee_id | UUID | связь с сотрудником |
| is_active | boolean | активен |
| created_at | timestamptz | дата создания |

Пароли хранятся только в виде стойкого хэша.

## 3.2. roles / user_roles — роли и права

Базовые роли:

- OPERATOR;
- ACCOUNTANT_PRODUCTION — учетчик;
- WAREHOUSE;
- QC — ОТК;
- SHIFT_MASTER;
- PRODUCTION_MANAGER;
- ECONOMIST;
- ADMIN;
- MANAGEMENT.

## 3.3. employees — сотрудники

| Поле | Тип |
|---|---|
| id | UUID |
| personnel_number | text |
| full_name | text |
| position_name | text |
| department_name | text |
| erp_id | text |
| is_active | boolean |
| valid_from / valid_to | date |

Табельный номер — основной бизнес-идентификатор сотрудника.

## 3.4. production_areas — участки

Например: пакетоделательный участок, печать, ламинация и т.п.

## 3.5. equipment — оборудование

| Поле | Назначение |
|---|---|
| code | внутренний код |
| name | наименование |
| production_area_id | участок |
| erp_id | ID в 1С |
| coverse_id | ID/код Coverse |
| is_active | используется ли |

## 3.6. products — номенклатура

Главный справочник должен синхронизироваться с 1С:ERP.

Поля:

- код ERP;
- артикул;
- наименование;
- единица измерения;
- активность.

## 3.7. operations — технологические операции

Нужны прежде всего для норм и сдельной оплаты.

Примеры:

- печать;
- резка;
- формирование пакета;
- упаковка.

## 3.8. downtime_reasons — причины простоев

Храним категорию и конкретную причину. Причина может быть:

- учитываемая в Availability;
- исключаемая из планового времени, если это заранее запланированная остановка.

## 3.9. defect_reasons — причины брака

Отдельный справочник, чтобы оператор и ОТК использовали одинаковые коды причин.

# 4. Смены и персонал

## 4.1. shift_types

Справочник шаблонов:

- DAY, 09:00–21:00;
- NIGHT, 21:00–09:00 следующего дня.

## 4.2. shifts

Конкретная смена.

Пример:

`2026-09-23 NIGHT = 2026-09-23 21:00 → 2026-09-24 09:00`.

## 4.3. employee_shift_assignments

Фиксирует, кто реально работал в смене и на каком оборудовании/операции.

Это критично для распределения сдельной выработки.

Поля:

- shift_id;
- employee_id;
- equipment_id;
- operation_id;
- started_at;
- ended_at;
- allocation_factor.

`allocation_factor` позволит распределять бригадную выработку, например 1.0 / 0.5 / 0.25.

---

# 5. Производственный план и запуск

## 5.1. production_orders

Производственное задание / заказ.

Основные поля:

- номер/ID ERP;
- продукт;
- плановое количество;
- плановые сроки;
- статус.

## 5.2. production_runs

Ключевая сущность OEE: конкретный запуск продукта на конкретном оборудовании.

Связывает:

- смену;
- оборудование;
- номенклатуру;
- производственный заказ;
- технологическую операцию.

Также фиксирует **снимок норматива** на момент запуска:

- `ideal_rate_per_hour`;
- `planned_qty`;
- `planned_start_at`;
- `planned_end_at`.

Норматив нельзя брать «текущий» задним числом после его изменения.

---

# 6. Фактический выпуск

## 6.1. production_output_events

Первичные записи выпуска.

Поля:

- production_run_id;
- occurred_at;
- quantity;
- event_kind;
- source_system;
- source_record_id;
- entered_by_user_id;
- status.

`event_kind`:

- INCREMENT — добавочное количество;
- CORRECTION — корректировка;
- FINAL — итоговая фиксация.

Для MVP рекомендуем передавать приращения, а не постоянно перезаписывать одну итоговую ячейку.

---

# 7. Брак и ОТК

## 7.1. defect_events

Один реестр брака, но с указанием, кто зафиксировал факт:

- OPERATOR;
- QC;
- SYSTEM_RECONCILIATION.

Поля:

- production_run_id;
- occurred_at;
- quantity;
- defect_reason_id;
- reported_by;
- is_confirmed;
- comment;
- source_system.

Важно: брак оператора и брак ОТК не заменяют друг друга. Они существуют параллельно для сверки.

---

# 8. Простои

## 8.1. downtime_events

Каждый простой — отдельное событие:

- оборудование;
- production_run;
- начало;
- окончание;
- причина;
- комментарий;
- плановый/неплановый;
- источник.

Продолжительность считается из `started_at` и `ended_at`.

Активный простой может иметь `ended_at = NULL`, поэтому его длительность можно показывать онлайн.

---

# 9. Склад и ГП

## 9.1. warehouse_receipts

Подтверждение количества ГП складом.

Поля:

- production_run_id;
- product_id;
- shift_id;
- received_at;
- quantity;
- warehouse_document_no;
- source_system.

Это **контрольная точка**, а не автоматическая замена производственного выпуска.

---

# 10. Факт 1С:ERP

## 10.1. erp_production_facts

Официально отраженный факт из ERP:

- ERP-документ;
- продукт;
- заказ;
- дата;
- количество;
- брак, если передается;
- внешний ID.

Таким образом можно строить цепочку:

Оператор → ОТК → Склад → ERP.

---

# 11. Нормативы

## 11.1. production_norms

Историзируемые нормы производительности:

- продукт;
- оборудование;
- операция;
- идеальная производительность в единицах/час;
- период действия;
- источник.

Нормативы не удаляются при изменении — закрывается `valid_to` и создается новая версия.

---

# 12. Сдельная заработная плата

## 12.1. payroll_rates

Историзируемый тариф:

- операция;
- продукт — опционально;
- оборудование — опционально;
- ставка за единицу;
- валюта;
- период действия.

## 12.2. payroll_periods

Расчетный период экономиста:

- месяц/диапазон дат;
- статус DRAFT / CALCULATED / VERIFIED / APPROVED / EXPORTED;
- кем рассчитан;
- кем утвержден.

## 12.3. payroll_lines

Расшифровка начисления сотруднику.

Каждая строка хранит **снимок**:

- сотрудник;
- смена;
- production_run;
- операция;
- подтвержденное количество;
- ставка;
- коэффициент распределения;
- сумма;
- основание.

Формула базовой строки:

`amount = approved_quantity × rate_per_unit × allocation_factor`

Правила премий, штрафов и доплат должны быть отдельными компонентами, а не скрытыми коэффициентами.

---

# 13. Импорт и интеграции

## 13.1. import_batches

Каждый импорт/API-проход:

- источник;
- тип данных;
- имя файла/endpoint;
- время начала/завершения;
- количество строк;
- количество ошибок;
- статус.

## 13.2. import_errors

Ошибки с номером строки, кодом и текстом.

Принцип: плохая строка не должна молча исчезать.

# 14. Аудит

Хранит:

# 16. Что является «истиной»

У разных задач разная контрольная точка.

### Для OEE

- время: смена + простой;
- производительность: выпуск производства + норматив;
- качество: подтвержденный брак по принятому бизнес-правилу.

### Для склада

Истина по принятым единицам — складское подтверждение.

### Для бухгалтерского/ERP-факта

Истина — отраженный документ 1С.

### Для сдельной ЗП

Берется **подтвержденная выработка**, прошедшая заданный маршрут проверки. Простая запись оператора сама по себе не должна автоматически становиться начислением.

---

# 17. Поля, которые нельзя терять

Для всех ключевых фактов обязательно сохраняем:

- кто;
- что;
- когда;
- смена;
- оборудование;
- продукт;
- заказ;
- источник;
- внешний ID;
- статус проверки;
- время создания;
- время изменения.

Это позволит восстановить любую спорную ситуацию по OEE и зарплате.
