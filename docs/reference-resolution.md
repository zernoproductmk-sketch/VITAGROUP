# Слой сопоставления справочников и производственных событий

## Зачем он нужен

Формы Coverse не содержат одинаковый набор ключей:

| Источник | Заказ | Линия | Артикул | Талон |
|---|---:|---:|---:|---:|
| Производство | да | нет | нет | нет |
| Простои | нет | да | нет | нет |
| ОТК | нет | нет | нет | нет |
| Учетчик | нет | да | да | да |
| Кладовщик | нет | нет | да | да |

Поэтому нельзя безопасно соединять записи только по времени.

## Разрешение справочников

Система сначала ищет точное совпадение:

- табельный номер → `employees.personnel_number`;
- линия → `equipment.code`;
- складской код/артикул → `products.code` или `products.article`;
- № заказа → `production_orders.order_no` / `erp_id`.

Если код во внешней системе отличается, используется таблица `external_reference_aliases`.

## Связка по талону

Учетчик и кладовщик могут быть связаны по `ticket_no`.

Это позволяет передать из строки учетчика к строке кладовщика:

- оборудование;
- продукт;
- смену;
- позднее — production_run.

Связка выполняется только при точном совпадении талона.

## Связка производственного выпуска

Форма производства дает № заказа. После загрузки плана ERP:

```text
№ заказа
  ↓
production_orders
  ↓
production_runs
  ↓
оборудование + продукт + смена
```

Поэтому отсутствие линии в форме выпуска не требует ручного угадывания, если ERP-план сформирован корректно.

## Брак ОТК

Текущая форма ОТК содержит:

- табельный номер;
- дату;
- смену;
- время;
- количество брака.

В ней нет заказа, линии, артикула или талона. Автоматическая привязка к production_run разрешается только если на момент приемки для сотрудника/смены существует **однозначный** производственный запуск через назначения персонала. В противном случае запись остается PARTIAL и не попадает в расчет OEE.

### Рекомендация по форме ОТК

Для надежной работы добавить хотя бы один устойчивый идентификатор:

1. **№ талона** — предпочтительно, либо
2. **№ заказа**, либо
3. **линия + артикул**.

## Статусы

- UNRESOLVED — еще не обрабатывалось;
- PARTIAL — часть справочников найдена, но не все обязательные;
- RESOLVED — событие однозначно связано;
- ERROR — техническая ошибка.

## Promotion

Только RESOLVED-события переносятся в рабочие таблицы.

```text
Coverse
  ↓
external_event_staging
  ↓ resolve
RESOLVED / PARTIAL
  ↓
promote
  ├── production_output_events
  ├── defect_events
  ├── downtime_events
  └── warehouse_receipts
```

Строки учетчика остаются контрольным слоем и связываются с кладовщиком по талону.

## API

- `POST /api/v1/reference/resolve` — выполнить сопоставление;
- `GET /api/v1/reference/unresolved` — показать нерешенные строки;
- `POST /api/v1/reference/aliases` — добавить ручное соответствие кода;
- `POST /api/v1/reference/promote` — перенести полностью разрешенные события в рабочие таблицы.

## Принцип безопасности

Если система не может доказать соответствие, она не делает предположение. Это особенно важно для OEE и сдельной зарплаты.
